## Feature

`CheckSystem query='version'` returns the commit hash + branch + dirty
state of the TM runtime **as loaded at process start** — not a live read
of the current codebase.

Design constraint, from the operator (paraphrased verbatim):
> *"It is not supposed to tell which hash is currently in the codebase,
> as the user can start the machine, pull, have a different hash in the
> codebase than it runs on, so it must be a 'start time loaded param' or
> something."*

## Why it matters

Three concrete incidents this generation:

1. **Field bug — version unknown.** The field agent's report carried
   `agent-executor:latest` with label `build_hash eac432c7…`. That is
   the *container image's* build hash, not the *TM runtime's* commit.
   When the container reap was reported, we could not answer "what
   version of TM was running when this fired?"

2. **Q1 check (i) — unanswerable.** "Did the field binary predate #90?"
   required asking the operator for a restart SHA. The machine could
   not self-report.

3. **Every future "did this merge fix it" question** depends on knowing
   the runtime version at the moment the symptom fired. Without it, we
   are always inferring.

## Design decisions (3 real ones, not one-liner)

D1. **Start-time capture, not query-time read.**
    Capture commit + branch + dirty state at server lifespan
    (`web_ui/backend/server.py::lifespan`, or module import in the agent
    core — whichever is the process root). Store as a module-level
    immutable constant. `CheckSystem` reads the constant, never `git`.

D2. **Git-less fallback.**
    Packaged installs (PyInstaller, pip, containerized) may not have
    `.git/`. Fallback path:
    - build-time-injected `_version.py` (generated by the packaging step)
    - or an env var (`TM_RUNTIME_COMMIT`) set by the launcher
    - or, at minimum, "unknown" — never fabricate a hash.
    Test this path.

D3. **Surface.**
    - `CheckSystem query='version'` for the agent.
    - `GET /api/version` for the panel — makes field reports self-
      describing and gives the operator a visible answer.
    The response should name: commit hash, branch, dirty flag,
    process-start timestamp, and (if present) the container's build hash.

## Scope

Small. One read, one fix, one test. Preconditions:
- Confirm where the process root is (server lifespan? agent main?)
- Confirm whether a `_version.py` or equivalent already exists
- Confirm current `CheckSystem` query vocabulary (does `'version'`

### Not shipped — the residual gap, if anyone wants it

1. **`GET /api/version` does not exist** (D3 asked for it). `/health` carries
   `revision` only — not branch, not dirty, not process-start time.
2. **No process-start timestamp** in any version payload. The value would make
   "was this the same process that produced that symptom?" answerable, which is
   the actual incident question from §"Why it matters".
3. **No container build hash** in the version payload (it is reported separately,
   per-container, on `ContainerStatusTool`).
4. **No `commits_behind_dev`.** Would require a readable `origin`; network is
   not guaranteed. Optional, and correctly optional — a version surface that
   fails when offline is worse than one that omits a field.

### Correction to the incident in the body

The §"Why it matters" instance 1 predates D1's fix: the field report could not
name the TM runtime, only `agent-executor:latest` + its image `build_hash`.
That question — *"what version of TM was running when this fired?"* — is now
answerable from the startup log line, `/health`, and `CheckSystem query='version'`.
**Do not re-file it as an introspection gap.** If a future field report still
cannot answer it, the defect is that nobody recorded the startup line, not that
the machine cannot self-report.

## Resolution — closed 2026-10-29 (Gen 54)

**Closed on the capability the ticket asked for:** the machine can now answer *"what version of
TM was running when this fired?"* without being told. D1 (start-time capture at the process
root, frozen in a module constant), D2 (git-less fallback that says `unknown` instead of
fabricating a hash) and the core of D3 (a `CheckSystem` surface) are in the tree, at the
locations recorded in the Gen 46 update above:

- capture: `web_ui/backend/server.py:228-247` — `_get_server_revision()` runs `git rev-parse HEAD`
  with `cwd=_project_root` at **import time**, frozen into `_SERVER_REVISION`; `_SERVER_BRANCH` /
  `_SERVER_DIRTY` captured in the same snapshot (`:250+`).
- read: `tools/workspace/check_system.py:195-215` — `_server_version()` imports those constants;
  its docstring states there is no subprocess git invocation here.
- fallback: `server.py:242-244` and `check_system.py:206-214` degrade to `unknown` / `False`.
- surfaces that exist today: `CheckSystem query='version'` → `{revision, branch, dirty}`; startup
  log lines at `server.py:669` (lifespan) and `server.py:5295` (uvicorn start); `GET /health` →
  `{status, service, revision}` (`server.py:3229-3235`); and, unplanned but correct,
  `ContainerStatusTool.runtime_commit` (`tools/container_control.py:55-60`).

That is enough for the three incidents in §"Why it matters": the field report can name the
runtime, and "did this merge fix it" no longer requires asking the operator for a SHA.

**What this closure does NOT claim.** Closure is on the capability, not on a clean sweep:

1. The two items under `### Verification still owed` above were **not** discharged. The dirty
   computation was still not read line-by-line, and the packaged-install fallback is still not
   confirmed to be covered by a test rather than only by an `except Exception`. Closing means
   "the operator's question is answerable", not "every branch is verified".
2. The four residual gaps in `### Not shipped` are unchanged and out of scope here: no
   `GET /api/version`, no process-start timestamp, no container build hash in the version
   payload, no `commits_behind_dev`. If wanted, they are a **new, smaller** ticket — do not
   reopen this one for them.
