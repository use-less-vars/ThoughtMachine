SYMPTOM (operator report): mid-session, at random, the conversation gains a user-role system notification `[SYSTEM NOTIFICATION] Configuration updated: base_url=https://api.deepseek.com/.` — even though the same endpoint had been working fine all along, i.e. nothing user-visible changed.

READ THE MESSAGE CORRECTLY FIRST (verified): the trailing `/.` is NOT part of the value. `agent/core/agent.py:356` builds `msg = "[SYSTEM NOTIFICATION] Configuration updated: " + ", ".join(changes) + "."` — the final `.` is the code's own sentence period. The reported value is `https://api.deepseek.com/` (trailing slash, no `/v1/`).

EMITTER (`agent/core/agent.py`):
- `_notify_config_change(old_config, new_config)` L315-358: loops `type(new_config).model_fields`, skips `sensitive_fields = {'api_key','stop_check'}`; `changed = old_val != new_val` — **raw `!=`, zero normalization in this method**; labels `enabled_tools`→"tools updated", `system_prompt`→"system_prompt updated", `provider_type`→`provider=…`, `workspace_path`→`workspace=…`, **else `f"{field_name}={new_val}"`** — so `base_url=…` is the *else* branch (base_url has no friendly label). Emits `Message(role='user', content=msg, is_system_notification=True)` (L358) after `log('DEBUG','core.config', f'NOTIFICATION CREATED: {msg}')` (L357).
- Called from `_apply_pending_config()` at L252 (hot-swap branch) and L277 (restart branch); `old_config = self.config` (live, L233), `new_config = self._pending_config` (L232).

THE GUARD THAT IS SUPPOSED TO STOP IT, AND WHY IT MISSES:

## 2026-09-21 — WS `continue_session` CASE 3: a queued query is drained BEFORE `load_session` on reconnect (silent query drop)

Reported by the operator during a live session on 2026-09-21 (agent call in a session that had been working fine; page refresh restored normal behaviour). **Status: OPEN — diagnosed only, no fix applied** (session was read-only for the repo). Recorded here as a known bug; the drain-ordering fix is entered in the UI sprint as a Wave 2 candidate (see `project/ui_sprint_overview.md`).

**Symptom (what the operator saw).** Submitting a query appeared to do nothing. Server log:

```
[server.ws] continue_session: CASE 3 - no active session! | bridge=False | _loaded_session=None | agent_is_running=False
```

**What the message means.** `continue_session` is a hand-written three-case state machine in `web_ui/backend/server.py` — Case 1 `server.py:1012-1039` (loaded, not running → `bridge.start(query)`), Case 2 `:1040-1059` (`agent_is_running` → `bridge.continue_session(query)`), Case 3 `:1061-1067` (neither → **drop the query**, WARNING + `status_message` "No active session — start a new one."). `bridge` is **per-websocket, in-memory** state: it only exists after *that connection* has received `new_session`/`start_session`/`load_session` (see the fresh-bridge construction at `server.py:2236-2246`, comment: the bridge sits IDLE with `_loaded_session` set so the first query hits Case 1). `bridge=False` therefore means: **this socket sent a query before it had ever bound a session.** The guard worked as designed; the defect is that a *user query* was the thing it discarded.

**Root cause — a frontend ordering bug on reconnect (`web_ui/frontend/src/components/SessionTab.jsx`).**
1. `sendCommand` queues any command issued while the socket is not OPEN (`:254-257`, `pendingCommandsRef` declared `:85`) and triggers a reconnect.
2. In `onopen`, the queue is **drained synchronously, first thing** (`:363-371`).
3. `load_session` is sent **one tick later**, deliberately deferred (`setTimeout(..., 0)`, `:385-397`).
So a `continue_session` submitted during a reconnect reaches the backend **before** `load_session`, against a socket whose `bridge` is `None` → Case 3 → query silently lost. Trigger conditions: backend restart (e.g. `uvicorn --reload` on a file save), sleep/wake, or a brief network blip — any of which also destroys the in-memory bridges server-side, so the client is guaranteed to reconnect into a session-less socket.

**Why a refresh "fixed" it.** Refresh tears down all sockets and remounts, so the new connection sends `load_session` first (nothing queued) → bridge re-created with `_loaded_session` → the next query hits Case 1. **No data loss**: the session, store and `~/.thoughtmachine/` were never affected — which is precisely why refresh restored everything.

**Confidence.** The ordering in (1)-(3) is **code-verified** (read in the file). That this specific ordering caused the operator's incident is **UNVERIFIED** — the browser console was not captured. The confirming evidence to look for next time: browser console `[SessionTab] WebSocket not connected. Command queued for retry.` followed by `[SessionTab] Sending queued command: continue_session`, and/or a nearby reconnect / `session_loaded` with a different id / "Session could not be loaded (it was lost in a restart)" (`SessionTab.jsx:~705`). The full state at entry is already logged one line earlier — `continue_session ENTRY` (`server.py:1004-1010`).

**Alternative not yet excluded.** There are **two websockets per session** (hub socket `App.jsx:309-338` = `list_sessions`/`get_open_sessions`; one socket per `SessionTab`). A `continue_session` sent over the hub socket would *always* be Case 3. The Case 3 log line does **not** print the socket identity, even though per-socket keys exist (`set_event_callback(event_callback, key=id(ws))`, `server.py:2246`) — a real diagnosability gap that makes the two cases indistinguishable from the log alone.

**Fix sketch (not applied).** (a) Drain queued user commands only **after** the `load_session` reply is acknowledged, not before it — i.e. gate the drain on the load ack rather than on `onopen`; (b) add the per-socket key to the Case 3 warning and to the ENTRY log; (c) make the "No active session" reply visible in the tab UI instead of only a status line, so a dropped query is never silent. This belongs to the same "silent drop" family the UI map already flagged (`docs/ui_map.md` PARTIAL rows, `Register 1`).
